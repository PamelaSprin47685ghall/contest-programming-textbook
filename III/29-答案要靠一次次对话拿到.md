# 29　答案要靠一次次对话拿到

打电话问路，对方看不见你，你也看不见地图。你说“我在一家面包店门口”，对方问“店对面是银行还是邮局”，你回答以后，他才说下一句。哪一方先开口、每句话说什么、说到哪里算完，双方都得心里有数；有一方说了句对方听不懂的话，这通电话就白打了。程序之间的对话也一样。

这一章讲**交互题**：程序拿不到全部输入，要通过提问，从评测程序那里一点点得到信息。先说清协议，再学会自己写一个本地的“对方”来测试，然后算清每问一次到底拿到了多少信息，最后说说遇到陌生的协议时该怎么办。

## 先写清双方说什么

交互题的题面会规定一份**协议**：评测程序先告诉你什么；你每次提问写成什么格式；它怎样回答；你怎样宣布答案；最多能问几次。写程序之前，先把协议抄成一张表，每一行写清“谁说、说什么、说完以后谁说”。

看一个小例子。评测程序心里想一个 1 到 n 之间的整数 x。它先输出一行 n。你每次输出 `? y`，它回答一个字符：`<` 表示 x < y，`>` 表示 x > y，`=` 表示猜中了。猜中以后你输出 `! y` 结束。问的次数不能超过最小的 q，使 2^q − 1 ≥ n。

做法就是[第二卷第 5 章](../II/05-每次划掉一半候选.md)那样的二分：候选是一段 [low, high]，问中点，按回答留下一边。交互和普通题只有两处不同。第一，每输出一个问题，都要调用 `std::fflush(stdout)`：`printf` 写出的字会先存在缓冲区里，攒够了才真正送出去；不刷新，对方就收不到问题，双方都在等对方，直到超时。第二，读到看不懂的回答时要立刻结束，而不是假装读到了什么继续问。

下面是**完整程序 A**。

```cpp
#include <cstdio>

int main() {
    long long n = 0;
    if (std::scanf("%lld", &n) != 1) {
        return 1;
    }
    long long low = 1;                    // 答案一定在 [low, high] 里
    long long high = n;
    while (low <= high) {
        long long mid = low + (high - low) / 2;
        std::printf("? %lld\n", mid);
        std::fflush(stdout);              // 先把问题送出去，再等回答
        char reply[4] = {0};
        if (std::scanf("%3s", reply) != 1) {
            return 1;
        }
        if (reply[0] == '=') {
            std::printf("! %lld\n", mid);
            std::fflush(stdout);
            return 0;
        }
        if (reply[0] == '<') {
            high = mid - 1;               // 秘密的数比 mid 小
        } else if (reply[0] == '>') {
            low = mid + 1;
        } else {
            return 1;                     // 看不懂的回答，立刻停下
        }
    }
    return 1;
}
```

`mid` 写成 `low + (high − low) / 2`，在 n 接近 10¹⁸ 时也不会因为 `low + high` 溢出。`%3s` 最多读 3 个字符，放进 4 个字符的数组正好，不会越界。找到答案就 `return 0`，循环正常结束（候选为空）说明对方的回答前后矛盾，返回 1。

## 把本地裁判当作真实的另一方

交互题没有现成的输入文件可以喂给程序。要测试，就自己写一个**本地裁判**：它扮演评测程序，按协议回答问题，最后判断对错、数清问了几次。

**片段：**

```cpp
// 本地裁判的全部 main；用法：./judge n x，秘密的数 x 在 1 到 n 之间
int main(int argc, char** argv) {
    if (argc != 3) {
        return 1;
    }
    long long n = std::atoll(argv[1]);
    long long x = std::atoll(argv[2]);
    int limit = 0;                        // 最小的 q，使 2^q − 1 >= n
    while ((1LL << limit) - 1 < n) {
        ++limit;
    }
    std::printf("%lld\n", n);
    std::fflush(stdout);
    for (int asked = 0; asked <= limit; ++asked) {
        char kind[4] = {0};
        long long y = 0;
        if (std::scanf("%3s%lld", kind, &y) != 2) {
            std::fprintf(stderr, "选手没有说完就停了\n");
            return 1;
        }
        if (kind[0] == '!') {
            bool right = y == x;
            std::fprintf(stderr, "%s，用了 %d 问\n", right ? "正确" : "答错", asked);
            return right ? 0 : 1;
        }
        if (kind[0] != '?' || y < 1 || y > n || asked == limit) {
            std::fprintf(stderr, "格式错误或问得太多\n");
            return 1;
        }
        std::printf("%s\n", x < y ? "<" : (x > y ? ">" : "="));
        std::fflush(stdout);
    }
    return 1;
}
```

`main(int argc, char** argv)` 让程序从命令行读参数：`argc` 是参数个数（含程序名本身），`argv[1]`、`argv[2]` 是后面两个参数的文字，`std::atoll` 把文字变成 `long long`，要 `#include <cstdlib>`。判决和问的次数写到 `stderr`，不会混进发给选手的话里。

两个程序要互相接上：裁判的输出是选手的输入，选手的输出是裁判的输入。在 Linux 上可以用两个**命名管道**，它们看起来像文件，写进去的东西会被另一端读到：

```text
mkfifo to_judge to_player
./judge 100 37 > to_player < to_judge &
./guess < to_player > to_judge
```

打开命名管道时，读的一方要等到写的一方也打开才继续，所以两边打开的先后要配好：裁判先打开 `to_player` 来写，选手先打开它来读，再各自打开另一个。顺序写反，两个程序会在打开管道时就互相等住。

有了本地裁判，就能像普通题一样对拍：随机挑 n 和 x，让程序跑一遍，看判决。我们这样跑了 300 组，n 从 1 到 10¹⁸ 量级，都判为正确，问的次数都没超过上限；也在 n = 1、2、3、7、8 时专门试了 x 取最小、最大和中间。

本地裁判还可以故意刁难：不事先选定 x，而是每次回答时，在仍然和所有回答相符的候选里，挑剩下最多的一边。这就是[第 26 章](26-知道哪里不能靠蛮力过去.md)的对手论证，它能逼出程序最坏情况下的问的次数。

## 每问一次，减少的究竟是什么

一次回答有 3 种可能，可 `=` 只出现一次，其余每次只有 `<`、`>` 两种。把所有提问过程画成决策树：每个节点是一次提问，节点本身对应“猜中”，左右两边对应 `<`、`>`。深度不超过 q 的这种树，至多有 1 + 2 + …… + 2^(q−1) = 2^q − 1 个节点，每个节点只能代表一个答案。所以 q 次之内一定猜中，需要 2^q − 1 ≥ n。程序 A 正好达到这个次数，不能再少。

一般地，每次回答有 k 种可能，q 次至多分开 k^q 种情况。算一道交互题“至少要问几次”，就是数清“候选有多少种”和“每问能分开几种”。反过来，题目给的次数上限，也常常提示该用什么办法：上限接近 log₂ n，多半要每次砍一半；接近 (log₂ n)²，可能是一层一层地二分。

**停笔 3**　猜数游戏里 n = 1000，最坏情况至少要问几次？为什么 9 次不够？

### 例题　古戈尔

公司有 N 名员工（N ≤ 10¹⁰⁰），编号是 1 到 N 的不同整数，组成一棵二叉树，根是 1 号。每名员工的左子树人数比右子树多 0 人或 1 人。程序每次输出一个员工编号，评测程序回答一行两个数：他的左、右下属，没有就是 0。问的次数不超过 70000，最后输出 `Answer N`。

样例输入（程序的提问和评测程序的回答交替出现，第 1、3、5 行是程序问的编号）：

```text
1
4 3
4
2 0
3
0 0
```

样例输出：

```text
Answer 4
```

1 号的下属是 4 和 3，4 号的下属只有 2，3 号没有下属。2 号不必问：4 号的右边没人，左边就至多 1 人。共 4 人。

这是 USACO 2015 年 3 月金组第一题[“古戈尔”](../USACO/金组/2014_2015/2015.03/P1.md)。

人数可能有 10¹⁰⁰，一个个数过去不可能。要用的是平衡条件：大小为 s 的子树，形状完全确定，左边 ⌊s/2⌋ 人，右边 ⌊(s − 1)/2⌋ 人。

先求右子树的大小 R，左子树就只剩 R 或 R + 1 两种可能。要分清这两种，比较大小为 R 和 R + 1 的两棵平衡树：R 是奇数时，它们只差在左子树（⌊R/2⌋ 和 ⌊R/2⌋ + 1）；R 是偶数时只差在右子树。于是沿着“差别所在的那一边”往下走，每层问一次，走到“大小为 0 还是 1”时看这个位置有没有人。这一步只问一条链，约 log₂ N 次。

求整棵树的大小，就沿右边一路往下：每层先递归求右子树，再用上面的办法问一条链定出左子树。右边的链长约 log₂ N，每层再问约 log₂ N 次，一共约 (log₂ N)² ÷ 2 次。log₂ 10¹⁰⁰ 约为 332，总数约 55000，在 70000 以内。

N 和编号可达 10¹⁰⁰，原题要用高精度整数，只需要加 1、减 1、除以 2 和判断奇偶。下面的片段先假设 N 不超过 10¹⁸，用 `long long`，把注意力放在提问的安排上；换成高精度时，只是把这几种运算换成对数字串的运算。

**片段：**

```cpp
// 位于 main 之前；先假设 N 不超过 10¹⁸
std::map<long long, std::pair<long long, long long>> known;   // 问过的员工

std::pair<long long, long long> ask(long long v) {
    auto it = known.find(v);
    if (it != known.end()) {
        return it->second;                // 问过的不再问
    }
    std::printf("%lld\n", v);
    std::fflush(stdout);
    long long left = 0;
    long long right = 0;
    if (std::scanf("%lld%lld", &left, &right) != 2) {
        std::exit(1);
    }
    known[v] = std::make_pair(left, right);
    return known[v];
}

// 已知 v 的子树有 s 或 s + 1 人，回答是不是 s + 1
bool one_more(long long v, long long s) {
    if (s == 0) {
        return v != 0;
    }
    std::pair<long long, long long> child = ask(v);
    if (s % 2 == 1) {
        return one_more(child.first, s / 2);         // 两种大小只差在左边
    }
    return one_more(child.second, (s - 1) / 2);      // 两种大小只差在右边
}

long long subtree_size(long long v) {
    if (v == 0) {
        return 0;
    }
    std::pair<long long, long long> child = ask(v);
    long long right_size = subtree_size(child.second);
    long long left_size = right_size + (one_more(child.first, right_size) ? 1 : 0);
    return 1 + left_size + right_size;
}
```

`main` 只需要输出 `Answer`，后面跟 `subtree_size(1)`，再刷新。`known` 记下问过的员工，同一个人不会问两次；`std::exit` 要 `#include <cstdlib>`。样例里，`subtree_size(1)` 先问 1，再求 3 号的子树：问 3，得到 1 人；然后 `one_more(4, 1)`：1 是奇数，问 4，再看左下属 2 是否存在，存在，所以左边是 2 人。共问 3 次，答案 1 + 2 + 1 = 4。

我们用一个按协议回答的本地裁判测试：员工随机编号，N 从 1 到 200 各种大小，300 组都答对；按先序编号时，N = 10¹⁸ 用了 1770 问。

## 不认识协议时，别猜一个“差不多”的

交互题最常见的错误，不是算法错，而是协议没对上。几条要守的规矩：

- 格式一字不差。题目写 `? y`，就不能写成 `?y` 或 `query y`；要求换行就换行。
- 每次提问以后刷新输出。
- 读取的次数和对方说的话完全对应：对方说一行两个数，就读两个数，不多也不少。
- 对方可能用特殊的回答表示“你已经出错”，比如 `-1`。读到它就立刻结束程序，不要接着问：评测往往在这时已经判了错，继续问只会让判决变成别的结果，掩盖真正的原因。
- 结束时不多说话，也不提前结束。

题面上看不懂的地方，比如“回答以后是不是总有换行”“多组数据时下一组从什么时候开始”，要去找题目给的样例交互和说明，而不是凭经验猜一个差不多的。题目要是提供了示范的交互程序或评测说明，先照着它把协议跑通，再写算法。

**停笔 5**　一道题规定“你最多问 20 次，第 21 次提问时评测程序会回答 `-1` 并结束”。某个程序第 21 次问以后，读不到 `<`、`>`、`=`，就当作 `>` 继续二分。会发生什么？程序 A 遇到这种情况怎样处理？

这一章的程序都在和另一个程序对话。先把协议写清，每问一次刷新；自己写本地裁判，用命名管道把两边接上，像普通题一样对拍；每次回答能分开几种情况，决定了至少要问几次；“古戈尔”靠平衡条件，每层只问一条链。能为一道交互题写出协议表、本地裁判和问的次数的估计，再读下一章。下一章是全卷的最后一章：把一个完整的证明从头带到尾，然后离开这本书，自己往前走。

## 核对

1. 问题留在缓冲区里，没有送到评测程序；评测程序在等问题，程序 A 在等回答，双方一直等到超时。本地手敲回答时，标准输出连着终端，很多系统对终端是按行刷新的，每个换行都会送出去，所以看起来没问题；接到管道或评测程序上就不按行刷新了。
2. 依次问 50（回答 `<`）、25（回答 `>`）、37（回答 `=`），裁判报告“正确，用了 3 问”。
3. 至少 10 次。9 次的决策树至多有 2⁹ − 1 = 511 个节点，分不开 1000 个数；2¹⁰ − 1 = 1023 ≥ 1000，10 次够。
4. 依次问 1、5、7、6、2、3。先沿右边问 1、5、7，7 号没有下属，大小 1；再看 6 号的子树是 1 还是 2 人：问 6，没有下属，是 1 人，5 号子树共 3 人；然后看 2 号的子树是 3 还是 4 人：3 是奇数，问 2，再看左下属 3 号的子树是 1 还是 2 人，问 3，没有下属，是 1 人，所以 2 号子树 3 人。4 号没有被问到。总数 1 + 3 + 3 = 7。
5. 评测程序已经结束，程序后面的输出没人读，再读也读不到东西；当作 `>` 继续，往往会因为写入已关闭的管道或读不到输入而异常退出，判决可能变成“运行错误”或“超时”，看不出原来是问多了。程序 A 读到不是 `<`、`>`、`=` 的回答就 `return 1`，读失败也 `return 1`，立刻结束。
