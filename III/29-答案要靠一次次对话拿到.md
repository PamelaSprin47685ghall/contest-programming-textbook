# 29　答案要靠一次次对话拿到

通常题目一开始把输入全给你。交互题不同：你先提问，出题程序才回答。不能等它把全部秘密吐出来再开始，也不能往输出里夹一行调试文字。

## 先写清双方说什么

秘密整数在 1 到一百万。你输出 `? middle`，对方回复：

|回复|含义|
|---|---|
|`LOW`|你的 middle 太小，秘密在后面|
|`HIGH`|你的 middle 太大，秘密在前面|
|`EQUAL`|猜中了|
|`-1`|对话已判失败，立即结束|

猜中后输出 `! middle`，完成。每次问完必须刷新输出，确保问题真的发出；否则你等回答、对方等问题，双方都会卡住。

**完整程序：**这是实际交互程序，不是一次输入全体回复的普通题。协议承诺回复一致，合法对话至多 20 次提问。遇到 EOF、`-1` 或其他无效回复，结束且不继续发问。

```cpp
#include <iostream>
#include <string>

int main() {
    int left = 1;
    int right = 1000000;
    while (left <= right) {
        int middle = left + (right - left) / 2;
        std::cout << "? " << middle << std::endl;
        std::string reply;
        if (!(std::cin >> reply) || reply == "-1") { return 1; }
        if (reply == "EQUAL") {
            std::cout << "! " << middle << std::endl;
            return 0;
        }
        if (reply == "LOW") { left = middle + 1; }
        else if (reply == "HIGH") { right = middle - 1; }
        else { return 1; }
    }
    return 1;
}
```

这里用 `std::endl` 同时换行并刷新。普通大批输出通常用 `'\n'` 更合适，不能为了学交互而给每个普通输出都增加刷新。

## 把本地裁判当作真实的另一方

本地检查器应启动程序，读一行 `?`，计算并立即写回对应答复，直到读到正确的 `!`。它还要检查范围、次数、格式、非法回复后是否停止，以及双方是否在等待未刷新的缓冲。不能只把预先写好的十行回复喂进去，就宣称所有秘密都能正确寻找。

一个对话开头可以是：程序问 `? 500000`；若秘密为 700000，裁判答 `LOW`。下一问应在 500001 到一百万内，而不是再次从 1 随机猜。这里故意不把一条固定交互记录写成唯一答案。

**停笔 1**　秘密为 1 时，第一条回复是什么？秘密为一百万时呢？20 次界来自什么，而不是来自反复试几个样例？

## 每问一次，减少的究竟是什么

在树上问到某点的距离，或问目标在哪个连通块，回复携带的信息不同。若一次能告诉目标位于删除某点后的哪一块，选重心可把剩余候选减半；若只回答“距离多少”，还需证明这些距离如何排除候选，不能照搬“问重心一定减半”。

对抗型回答未必预先固定一个秘密，但必须始终与至少一个合法秘密一致。算法要维护全部可能候选；裁判允许撒谎几次时，还需把“剩余撒谎预算”放进状态。题目没有给这种模型，就不应凭空增加。

通信题则往往由两个程序分持数据，设计它们交换哪些位。例如一方有集合 A，另一方有一个索引 i，询问是否在 A。若只需一次查询，可以传 i 再回复一位；若限制单向且必须支持任意 i，第一方可能需要传整份足够区分集合的信息。先定谁先说、是否可来回、是否共享随机数，再谈下界或哈希。

**停笔 2**　程序把调试语句 `middle is 7` 也写到标准输出，会破坏什么？本地调试该写到哪个通道？

## 不认识协议时，别猜一个“差不多”的

读题要核对：编号从哪开始；提问是否计入总数；失败标记；最后答案格式；是否必须退出；响应顺序。多测试用例时，前一个秘密的候选表不能带到下一例。发出不合法问题的后果由协议决定，不能把本地裁判宽容当作正式保证。

**停笔 3**　若只忘刷新，二分公式仍正确，程序能完成吗？为什么这是完整算法的一部分，而不是无关的输入输出小节？

## 核对

1. 分别为 `HIGH`、`LOW`。每次严格去掉中点及不可能的一半，候选按一半缩小，一百万小于 `2^20`。
2. 裁判无法按协议解析；调试用 `std::cerr`，正式协议内容仍只放标准输出。
3. 可能双方永远等待。提问只有送达以后才产生回答，发送与本地算出问题不是同一件事。
